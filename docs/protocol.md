# プロトコル（2026-10-31 実機で確定）

出どころは 3 つ。**推測は書かない**。すべて再現できる形で残す。

1. ベンダ CD の `DDS140.exe`（.NET）の逆コンパイル（ilspycmd）
2. `USBInterFace.dll`（WinUSB ラッパ）の静的解析（Ghidra）
3. 実機（Windows, `8312:8312`）に対する自作ハーネスと Python 実装での実測

逆コンパイルと実測の結果は `vendor/`（Git 管理外）ではなく、
この文書と `dds140/const.py` に落としてある。

## 1. 転送は 2 種類だけ

### コマンド（制御転送・常に 1 バイト読み戻し）

| フィールド | 値 |
|---|---|
| bmRequestType | `0x80`（device→host / vendor / device） |
| bRequest | コマンド番号（下表） |
| wValue | 引数（16 bit） |
| wIndex | `0` |
| wLength | `1` |

戻り値は基本**コマンド番号のエコー**（`cmd(36,0)` → `36`）。
例外は `cmd 144` で、こちらは個体キャリブレーション値が返る。
`0x00` が返るコマンド（34/35）もあるので、戻り値は成否判定に使えない。

### 波形データ（EP `0x82` interrupt IN 1024B）

ベンダ GUI は **32 KiB ずつ** `WinUsb_ReadPipe` に投げ、それを
`ReadDataCount ÷ 32 KiB` 回繰り返す。実際の通し読みでも同じ結果になる。

**データ形式（実測で確定）**: 8 bit / サンプル、2 バイトで 1 組。

```
byte[0] = CH1, byte[1] = CH2, byte[2] = CH1, byte[3] = CH2, ...
```

つまり `raw[0::2]` が CH1、`raw[1::2]` が CH2。CH1 の無入力時の値は
この個体のキャリブレーション値 `cmd144[1] = 117` と一致した（誤差 <1 LSB）。

**フレーム先頭の整定**: 実測で、各フレームの先頭 2〜10 サンプルは
ADC/マルチプレクサの整定で大きく跳ねる（無入力でも 0x5f〜0xff まで振れる）。
ベンダ GUI は `DataPreDisposal` + トリガ位置で隠している。
クライアントでは `--skip 16` のように先頭を捨てると素直になる
（本実装の `capture(skip=N)`）。

`GetRawData4Read(0/1)` が返すのは、この生データを間引いて
[min, max, first, last] の 4 バイト/px に詰め直した**表示用**配列で、
`DataPreDisposal()` が作る。**macOS 実装では不要**（自前で間引く）。

### cmd 80 の状態値

| 値 | 意味（推定を含む） |
|---|---|
| 33 (`0x21`) | 1 フレーム準備完了 |
| 44 (`0x2C`) | 取得中 |

`51` の直後は 44 が返り、少し待つと 33 になる。かかる時間はレート依存:

| レート | 33 までの実測時間 |
|---|---|
| 100 MS/s | 0.3 s |
| 39 kS/s | 1.8 s |
| 240 kS/s | **6.8 s** |
| 625 kS/s | 〜0.5 s |

**遅いレートでは 15 秒待つ前提でポーリングする**（実装済み）。

## 3. サンプルレート（cmd 148 下位ニブル）

**重要（2026-10-31 実測）: cmd 148 の値は「ラベル」であって、実際に届くデータの
レートではない。** 内蔵の 1 kHz 標準矩形波を入力に入れて測ると、実際の
レートはラベルの 1/22〜1/28 だった（`python3 -m dds140 calib-rate`）。

| ラベル | 実測の実効レート | 比率 | 備考 |
|---|---|---|---|
| 100M | 3.58 MS/s | ×27.9 | 転送レート（USB 上限 ~3.6-4 MS/s）と一致。**時間軸が正しい唯一のモード** |
| 10M | 447 kS/s | ×22.4 | データは 3.9 MS/s で届く＝サンプル欠落あり。時間軸は不正確 |
| 625k | 28 kS/s | ×22.3 | 同上 |
| 240k | 4 kS/s（?） | ×60 | 転送は 240 kS/s で実時間。内容が入力と一致せず未解明 |
| 39k | 測定不能 | — | 矩形波が判別できない |

実効レートは `~/.dds140/rates.json` に保存され、CLI/UI は自動でそれを使う
（校正値が無いときはラベルを使う）。

**時間軸・周波数を信用できるのは 100M 設定だけ**（転送が実時間と同じ 3.58 MS/s）。
10M/625k はデータがラベルのレートより速く届く = どこかでサンプルが落ちている。

### 元のラベル表（cmd 148 の値そのもの）

| 値 | レート | 実測 |
|---|---|---|
| `0x0` | 100 MS/s（2ch 同時） | ✅ データ取得を確認 |
| `0xC` | 10 MS/s | ✅ |
| `0x8` | 625 kS/s | ✅ |
| `0xB` | 39 kS/s | ✅ |
| `0xA` | 240 kS/s | ✅（待ち時間が長い） |
| `0x0` + cmd36 bit0 | 200 MS/s（合成） | ⚠️ 実測では 2ch と同じ ~3.55 MS/s（下記） |

※ どのモードも実際のサンプルレートはラベルより 1 桁小さい。上の「実効レート」表を見ること。

### 合成モード（`cmd 36` bit0 = ベンダ GUI の「200M」）

ベンダ GUI の時間軸ノブ 9 番がこれを立てる。命令自体は通る（エコーあり）が、
**実測では「2ch のデータを 2 倍のレートで取る」ようにはなっていなかった**。

| 確認したこと | 結果 |
|---|---|
| `cmd 36` bit0 | 送ると通り、`200M` 表示相当になる |
| データ構成 | **2 バイト/サンプル（CH1, CH2）のまま**。偶数=CH1、奇数=CH2 |
| 奇数バイトの素性 | CH2 のレンジを変えると追随する（= CH2 である） |
| 実効レート | 3.55 MS/s（2ch モードの 3.58 MS/s と同じ。**2 倍にならない**） |
| 転送量 | 7.4〜7.5 MB/s（2ch と同じ。USB 帯域で頭打ち） |

つまり USB で見える限り「200M はタイムベースのラベル」であって、ADC 2 個を
インターリーブした 2 倍サンプリングにはなっていない。ベンダ GUI の
`g_CurrentFreq = 160000`（160 MHz）は内部値で、転送されるデータには現れない。

本実装はこの設定を **「200M 合成タイムベース」**として扱い、
校正値（`calib-rate`、実測 3.548 MS/s）で時間軸を補正する。

`cmd 148` の bit4 (`0x10`) は **CH1 の AC 結合**、
`cmd 36` の bit4 (`0x10`) は **CH2 の AC 結合**。

## 4. 垂直レンジ（cmd 34 / 35 と cmd 36 のビット）

ベンダ GUI の「V/div」は 6+1 段。CH1 は `cmd 34` と `cmd 36` bit3、
CH2 は `cmd 35`（bit6 = 64）と `cmd 36` bit1-2 の組み合わせで選ぶ。

| V/div | CH1 `cmd34` | CH1 `36.bit3` | CH2 `cmd35` | CH2 `36.bit1-2` | dScale | 係数の cal | ゼロ点の cal |
|---|---|---|---|---|---|---|---|
| 2V | 0 | 1 | 0 | 0 | 10.0 | 3 / 4（1V） | 1 / 2 |
| 1V | 0 | 1 | 0 | 0 | 10.0 | 3 / 4 | 1 / 2 |
| 500mV | 2 | 1 | 0 | 2 | 5.0 | 8 / 11 | 14 / 15 |
| 200mV | 0 | 0 | 64 | 0 | 2.0 | 6 / 7 | 1 / 2 |
| 100mV | 2 | 0 | 64 | 2 | 1.0 | 9 / 12 | 18 / 19 |
| 50mV | 4 | 0 | 64 | 4 | 0.5 | 10 / 13 | 16 / 17 |

電圧換算（ベンダ GUI と同一の式）:

```
volts = (code - zero) * dScale * (cal_gain * 2 / 255) / 255 * probe_atten
```

（`probe_atten` は 1x = 1.0、10x = 10.0。入力定格は 1x で ±5V、10x で ±50V。）

レンジを変えるとゼロ点も変わる（減衰器のオフセットが別個体値）。
**実測**: 1V → 500mV → 200mV → 100mV → 50mV と切り替えて
`cmd34`/`36` の値が期待どおり変化し、データも取得できた。
ただし無入力なので「減衰量そのもの」は未確認（信号を入れて要確認）。

## 6. 1 フレームの手順（実測どおり）

```
1. DeviceOpen（WinUSB / libusb で interface 0 を claim）
2. cmd144 を 1..19 読む（キャリブレーション）
3. cmd 34, 35, 36, 148 でレンジ・レート・結合を設定
4. cmd 51（取得開始）
5. cmd 80 を 33 になるまでポーリング
6. EP 0x82 から N バイト読む（32 KiB ずつ）
7. 2 バイト 1 組で CH1/CH2 に分ける
```

`SetInfo` / `SetStableEnableOrNot` / `SetReadEnableOrNot` / `DataPreDisposal` /
`TrigDataPrepare` / `AutoMeasurement` は **GUI 側の後処理**であって
USB には出ていかない。macOS 実装では自前の処理に置き換える。

`AiReadBulkData` は非同期（OVERLAPPED）で ReadPipe を投げるだけなので、
DLL を直接叩く場合は読み出し完了を待つ必要がある（実測で踏んだ）。
libusb の同期読み出しならこの問題は起きない。
